# Upstream and distributed artifacts

This grant covers this repository's own expressions: `flake.nix`, `pin.nix`, `update-version.sh`, the README, and these documents. One tracked file is not ours: `.github/workflows/update-branches.yml` is installed and refreshed from flake-lib's templates, and flake-lib's tree at the revision this flake locks (`e102eb2e5b3f958e8bf23695e60215dcbfc89bfd`) holds no `LICENSE` or `LICENSE.md`, as the revision previously locked here did not — so the terms of that file are unstated at their source rather than granted here.

This flake names upstream rather than carrying it. `pin.nix` records a release version and the fixed-output hash of each platform's tarball at `https://github.com/coder/code-server/releases/download/v<version>/code-server-<version>-<os>-<arch>.tar.gz`, and the tarball is fetched only when a derivation is built. Evaluating this flake, or promoting its repository, therefore conveys no upstream code to anyone. Building and then serving the result is a different act: fetching `packages.<system>.code-server` from a binary cache, or installing it, conveys the unpacked upstream release tree, and what follows is what reaches the recipient with it.

`packages.<system>.code-server` — and `packages.<system>.default`, the same derivation — is upstream's prebuilt release asset unpacked verbatim: the install phase copies the tree and wraps the launcher, with fixup disabled and no patch applied, so the licensing inside it is upstream's and unchanged. code-server is MIT (`https://spdx.org/licenses/MIT.html`), `Copyright (c) 2019 Coder Technologies Inc.`; we read that from upstream's own `LICENSE` at tag `v4.143.1`, and nixpkgs records the same SPDX identifier for its `code-server` package at the locked revision. MIT's condition on a copy — that the copyright and permission notice be included — is discharged inside the output rather than in this repository: `$out/LICENSE` is upstream's file byte for byte, matching sha256 `872184c17fe5a3379da02acd21949ea2fcf4793bd4a3b920a96ba8b147741745`.

The same tree carries the notices of what upstream incorporated. `$out/ThirdPartyNotices.txt` is upstream's own notice file, naming each component it drew from with its version and source URL and reproducing that component's license text, and 244 further license files sit beside their packages under `$out/node_modules` and `$out/lib/vscode/node_modules`. Because the install phase copies the tree and fixes nothing up, every one of these lands in the output at the path upstream shipped it at. Seven are attribution notices of the kind Apache-2.0 §4(d) sends along with the work they accompany: five under `$out/lib/vscode/node_modules/@microsoft/`, plus `@vscode/deviceid/NOTICE.txt` and `vscode-oniguruma/NOTICES.txt`. Each of those packages declares MIT for itself in its own `package.json`, and which incorporated Apache-2.0 component each notice covers is something we have not determined. There is no top-level `NOTICE` to carry, because code-server itself is MIT rather than Apache-2.0. Every extension under `$out/lib/vscode/extensions` declares MIT in its own `package.json` except `copilot`, whose `SEE LICENSE IN LICENSE.txt` resolves to a Microsoft MIT text shipped in that same directory.

The bundled interpreter at `$out/lib/node` is upstream's prebuilt Node.js — it reports `24.22.1` when executed, not the `24.21.0` of the nixpkgs interpreter the wrapper puts on `PATH`, and it, not the consumer's nixpkgs, is what runs the server. Node.js is published under MIT; we found no license text for it anywhere in the unpacked tree, so that identifier is asserted from the Node.js project rather than from a file in the output, and whether the notice obligation for the prebuilt binary is satisfied is upstream's release packaging, which we have not verified. The statically bundled components that interpreter reports — ICU, OpenSSL, zlib, zstd, SQLite, and the rest — are likewise Node's release packaging, not something this flake selects.

Almost all of that inventory is permissive. The copyleft we found in the unpacked tree is `jschardet`, at LGPL-2.1+ under `$out/lib/vscode/node_modules/jschardet/LICENSE`, matching the identifier its own `package.json` declares, and upstream's notice file reproduces the terms of fish-shell and of zsh — most of fish is GPL-2.0, and parts of zsh's shell functions are GPL — for material carried by the bundled `terminal-suggest` extension, whose own declaration is MIT and whose notices travel in `ThirdPartyNotices.txt`. A text search for the GPL name also surfaces `$out/node_modules/argparse/LICENSE`, which is the Python Software Foundation's history-and-terms text and grants nothing copyleft. That inventory came from searching the built output, not from auditing the two dependency trees component by component, so treat the absence of anything further as unverified rather than as settled.

What a consumer's nixpkgs adds belongs to the wrapper, not to the server. `wrapProgram` puts `pkgs.nodejs` on `PATH` for child processes, so the runtime closure of the output is 37 store paths: this derivation, `nodejs` 24.21.0, `bash`, and the 34 store paths behind those two. Store paths rather than projects, because several packages contribute more than one output — `libuv`, `zlib` and `openssl` each add a `-dev` output, `zlib` a `-static`, `openssl` a `-bin`, nodejs an `-npm` and a `-corepack`, and GCC a `lib` and a `libgcc` under the `gcc` name plus a second `libgcc` under the `xgcc` name. Every identifier in this paragraph is taken from nixpkgs' recorded `meta.license` at the locked revision `5adc50831c259f87faeb09ddf930d43597197473`, not from the packages themselves, so what this states is the distribution's own accounting. The copyleft members are `bash` GPL-3.0-or-later — in the closure only because our wrapper script runs under it — GCC's `lib` and `libgcc` outputs GPL-3.0-or-later, a recorded attribute that names no runtime-library exception even though the same revision defines a `gccException31` license (`GCC-exception-3.1`), `glibc` LGPL-2.0-or-later, `libunistring` LGPL-3.0-or-later, and `libidn2` under the LGPL-3.0-or-later, GPL-2.0-or-later, GPL-3.0-or-later union. The rest is permissive: `icu` Unicode-3.0; `openssl` and `simdjson` Apache-2.0; `ada` and `simdutf` under the Apache-2.0 or MIT choice; `zlib` Zlib; `sqlite` the SQLite blessing; `zstd` and `gtest` BSD-3-Clause; `brotli`, `c-ares`, `llhttp`, `merve`, `nbytes`, `nghttp2`, `nghttp3`, `ngtcp2` and `uvwasi` MIT; `hdrhistogram_c` public domain; and `libuv`, whose recorded terms are the widest union in the closure — MIT, ISC, BSD-2-Clause, BSD-3-Clause, or CC-BY-4.0. Those five are nixpkgs' reading of three files libuv ships: `LICENSE`, the Expat text; `LICENSE-extra`, the Joyent grant plus the externally maintained libraries, which is where the ISC and BSD-2-Clause legs come from; and `LICENSE-docs`, whose text is Creative Commons Attribution 4.0 International and whose name is the only statement of its scope upstream makes, so we record it as the documentation's license on that basis. The two libuv store paths in this closure are a `lib` and a `dev` output holding `lib`, `include` and `nix-support`, and neither carries any Creative Commons text, so the documentation that leg governs is not what we convey. nixpkgs marks every leg of that union `free = true` and `redistributable = true` at the pinned revision, so nothing in the closure is flagged non-free by the distribution's own record, and a revision that flagged the CC-BY family differently would be worth re-reading on a bump. None of these appear in the output's own license files; they arrive from whichever nixpkgs the consumer follows, so the consumer's own accounting governs them and this document only names what the wrapper pulls in.

The flake's other outputs carry nothing of upstream's at all. `packages.<system>.update-version` is this repository's own script, `packages.<system>.update-branches`, `formatter` and `checks.<system>.formatting` come from flake-lib, and `update-version.sh` reads release metadata and prefetches hashes without ever committing upstream content. We ship no patch of our own against upstream's code, so conveying a built output adds nothing to the corresponding-source obligation that upstream's own release already carries.
